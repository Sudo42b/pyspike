The currently-cited fixture TypeError at line 74 is only the FIRST failure surface.

**Breakage A — torch backend incompatibility (line 74, npu_with_pattern fixture):**

```python
# CURRENT (line 74) — numpy RHS to torch.uint8 CUDA tensor: TypeError
npu.mem.l2_byte(0)[100:200] = np.arange(100, dtype=np.uint8)
```

Fix: switch the RHS to a torch tensor on the same device as the destination slice:

```python
_dst = npu.mem.l2_byte(0)
_dst[100:200] = torch.arange(100, dtype=torch.uint8, device=_dst.device)
```

Add `import torch` at the top of the file (numpy stays — see Breakage C, lines that
synthesize *expected* `bytes(...)` for DDR comparison can keep using `np.arange`
because DDR is CPU and the comparison is against a Python `bytes` object).

**Breakage B — removed `riscv.gtx.ddr` module (line 112):**

```python
# CURRENT (line 112, inside test_deferred_store_flush_diff)
from riscv.gtx.ddr import ensure_ddr
...
ensure_ddr(npu.mem, 0x1000 + 100)
```

Fix: drop the import; call the method on `GtxMemory` directly:

```python
npu.mem.ensure_ddr(0x1000 + 100)
```

**Breakage C — removed `_ddr_bytes` attribute (lines 118, 123, 158, 230, 277):**

The DDR backing array is no longer a numpy array exposed as `_ddr_bytes`; it's a
`DDR_MEMORY` instance owning a CPU torch.uint8 tensor. Replacement pattern (DDR is
CPU-resident, so `.tobytes()`-equivalent on a torch tensor works via `bytes(...)`
or `.numpy().tobytes()`):

```python
# CURRENT
bytes(npu.mem._ddr_bytes[0x1000:0x1000 + 100])

# REPLACE WITH  (one of, pick the simpler — read returns a CPU slice already)
bytes(npu.mem.ddr.read(0x1000, 100).numpy())
# OR equivalently:
bytes(npu.mem.ddr.raw()[0x1000:0x1000 + 100].numpy())
```

Apply this rewrite at all five sites (lines 118, 123, 158, 230, 277). The `np.arange`
RHS at lines 124, 159, 231, 278 stays — those produce a Python `bytes` for comparison,
not a torch RHS.

**Pre-flush DDR-untouched assertion (line 118-119):** the test asserts
`pre_flush == bytes(100)` (all zeros). After `npu.mem.ensure_ddr(0x1000 + 100)` the
freshly-grown region is zero-initialised by `DDR_MEMORY.ensure` (`torch.zeros(...)`),
so this assertion still holds — no logic change needed there beyond the API
substitutions above.
